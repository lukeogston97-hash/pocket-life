# How the code is laid out

How it works now. How it got this way (the audits, what was found, the measurements at the time): docs/history/code.md. Which file holds what: CLAUDE.md, "Where things are". How to add things: docs/adding.md.

## The page and loading
- test/ is the next version; the root is the released copy (tools/release.sh). The same files in each: index.html (the page, loading screen and loader), style.css, game/*.js (the game in parts), game-data.json (all content), icons/, manifest.webmanifest, privacy.html. three.js r170 from jsDelivr through an import map. No build step.
- The loader fetches game-data.json fresh, then style.css and the parts with the version and build added to their addresses, so phones never mix old and new files. The parts (PARTS in index.html, in order) are joined and run as one module: one shared scope, so a part can use anything from an earlier part, and functions can use later ones once everything has run. A new part goes into PARTS (release.sh copies the whole game/ folder).
- The loading screen is in index.html's own head (#boot), so it shows the moment the page opens and covers everything until the world has been drawn twice (window.__frames). Anything that goes wrong on the way says so there with Try again: the data or code not arriving, three.js not arriving, 3D not starting, the style sheet failing; a plain script catches a browser too old for the loader.
- The import map is in the head, followed by modulepreload links for three.js and its add-ons (the map has to stay above them). The font's style sheet doesn't hold the page up.
- What a shared link shows: the description and og: tags in index.html and icons/share.jpg (1200 x 630), always pointing at the release link. The app icons (favicon.png, apple-touch-icon.png and the two in the manifest) and the share picture are drawn from the game by `python3 tools/tests/pictures.py`: run it when the look changes.
- manifest.webmanifest says "display": "browser" on purpose: an iPhone gives a home screen app its own storage, so it would be a new device with no person. Only change it once a person no longer lives in the browser's storage.
- theme-color follows the sky (setTheme in game/needs.js). robots.txt (root only) keeps test/ and the project's folders out of search results. #app is `overflow: clip` (with `hidden`, a focus past its edge could leave the game scrolled). preserveDrawingBuffer is off; the inventory's pictures have their own small renderer.
- The main menu says "Early access" beside the version number (Luke's pick), inside #menuVer, so the 5 taps for admin mode land on it too.
- Can't reach the world: after two tries with no answer (net.fails in online.js) the main menu says "Can't connect. Trying again…"; a connection that hangs for 10 seconds is dropped and tried again.

## Content and shared rules
- game-data.json holds all content, with a "help" section explaining every part. Most additions are a data edit (docs/adding.md). New items show up by themselves in the admin's Add list, the Inventory and Recipes (with a picture drawn from the 3D model); keep that true for anything new.
- test/game/rules.js is the one copy of every rule both the game and the server work out (needs maths, berries growing back, fires and fuel, seats, the placing grid, crops growing, kinds of item, where a claim can go, the chat filter). It's the first part, and `python3 tools/worlds.py test-build` copies it to server/src/rules.js (never edit that copy). Keep it plain: no THREE, no page.
- `python3 tools/worlds.py check` (run by lint.py and by test-build) says in plain words what's wrong in game-data.json (an item that doesn't exist, an unknown shape, a weight that isn't whole, a section with no help note...) and fails if the server's copies (game.json, words.json, src/rules.js, worlds.json's test version) are out of date.

## The world and drawing
- The world is settings.worldSize metres square (100), with thick forest past the edge. The clearing round the start is laid out from its own random numbers, the rest from a second set, and anything added later gets its own seed (withOwnRand), so nothing already there moves. The layout must never move: the `layout` check compares it with layout-baseline.json.
- Keep it light for phones: copies of a shape are one InstancedMesh, split into chunks of the map, with simpler shapes far off (LOD). Grass is only drawn near the camera. Loose items whose shapes are shared (sharedGeo in items.js: sticks, stones, logs, berries) are drawn together, one InstancedMesh per shape (batchFor in world-items.js); build any item that lies about in numbers with sharedGeo.
- Below about 45 frames a second the game lowers its sharpness a step (pixel ratio, never below 1). Once it has settled (speedSettled in camera.js) the main menu draws about 30 times a second.
- Other people: only the nearest GRAPHICS[gfx].people (30 high, 20 medium, 12 low) have a body (showBody in others.js); the rest are hidden markers.
- Placed things level the ground under them (land.js setFlats), and trees, rocks, bushes, tall grass, grass and loose items near them move up or down with it (liftNear in world-build.js): placeables.md, Flat ground.
- What's in the way when walking: spots (nature.js) mark rocks, logs, stumps and tree trunks as solid, and bushes and farm fields as WALK_THROUGH (they take room but are walked through). Routes: A* on half-metre cells (findPath in moving.js), corners cut where clearLine allows.
- UI details that bite: bars centred with `left: 50%; transform: translateX(-50%)` need `width: max-content` (and a max-width); every box people type in is 16 px on touch screens, or an iPhone zooms the page in (the `menu` and `admin_phone` checks look).

## The server
- server/ is a Cloudflare Worker (pocket-life) with one Durable Object holding the whole world (live), at wss://pocket-life.misty-glade-6e8e.workers.dev/world (the game finds it through "server" in game-data.json). Cloudflare builds and deploys it from the server folder on every push to main. PROTOCOL in index.js and proto in the game's hello must match.
- Nothing about the game is kept on the phone but settings (graphics, mutes), tips seen and the phone's random id. The server holds people (one key each, p:<id>), the world, feedback and reports.
- Who's connected: sockets() works it out once per message or tick (fresh() clears it), socketOf(who) and isOnline(who) look people up. Always save an attachment with this.attach(ws, me), never ws.serializeAttachment. me.said (recent chat kept for reports) is trimmed so the attachment stays under Cloudflare's 2 KB.
- A short break in the connection: for away.comeBackSeconds (15) the person stays where they are; the game keeps what it finishes in an outbox (sendAct, flushOutbox in online.js; up to 8 things, 30 s), sends it on reconnecting and asks for its person ('sync'). Longer, and the game jumps to where the server has them.
- Respawning: an item with startInWorld and spawnsNear (trees or boulders) tops up by itself (respawnPlan in server/src/nature.js); topping up only saves when something was added.
- Old things fade (fadeOld in server/src/nature.js, once an hour): a thing gets the time it was put down (laidNow in shared.js) when a person drops it, chops or mines it out, spills it by dying or going, or takes a campfire apart, or the admin adds it; left outside a camp for settings.fadeDays (7, a live setting) it's gone. The world's own sticks and stones never fade. Inside a camp the days don't run. Games are told with 'gone'. Check: fade.mjs.
- Errors: the server's tick (per person) and each message are caught; noteError adds a "Server error (where)" note to the Inbox, once an hour per problem. In the game, frame() catches an error and carries on, and reportError (online.js) sends each problem once (5 a visit at most) as a "Game error" note. Repeats are counted, not repeated.

## Cloudflare's free plan
- 100,000 requests a day (20 incoming WebSocket messages count as 1, plus connections and alarms) and 100,000 storage writes a day; past either, things fail until 9:30 am Darwin. The $5 a month Workers Paid plan takes the daily caps away (Luke's call).
- So: at most settings.maxPlaying (20, a live setting) play at once and the rest wait in line on the main menu ('line', 'turn'); walks are sent once with where they end (plus every 2.5 s) and other games walk them along findPath; people are saved straight after doing something, but walking and needs at most every 5 minutes (SAVE_EVERY), and people away at most every hour (touchLater) since the server can play them forward again; picking berries saves once however many were picked. Every write goes through put() so it's counted; the admin's Server tab shows today's use.
- `python3 tools/tests/load.py 300` runs the real server in memory with 300 people away and 20 playing; at the player limit it uses about 81,000 writes a day. Still open as it grows: each pick-up or drop costs 2 writes, the whole world is one stored value (2 MB cap), every person is loaded at start, and about 18 claims fit in the 100 m world.

## Guards: the server never takes a game's word
- Reach: your person has to be within 4 m of what they pick up, pick, cut, chop, mine or put down, and by the pond to drink (guard.js near, spotOf). The server keeps where your person is: a game that says they jumped, left the map or moved while asleep is sent back ('pos'). Walks are allowed up to 25 m at once, refilled at 1.6 times walking speed.
- The layout (layoutData in online.js) comes from the first game of each new build, and the admin's game has the final word; isThing and isPlant refuse a tree, rock, bush or plant the layout doesn't have; which rocks are boulders comes from the layout too.
- Placing (cantPlaceAt in guard.js): not within 2.5 m of the edge, not in the water, not within half a metre of the middle of a tree, rock or bush; each a little looser than the game's own check, so a real game is never refused.
- Time (worked in guard.js): each person earns a second of work per second, up to 90 saved, and a thing that takes S seconds costs 0.6 of S. A real game has always earned it. Because the released game may wait an older, shorter time, a test build can raise a time by up to two thirds; more than that, release soon after.
- Text: clean (shared.js) takes out control and unseen marks; blank refuses a name or chat line with nothing to see. Kinds of message, recipes, items and fuels are only ever the server's own (Object.hasOwn).
- Limits: spam limits per message (LIMITS in shared.js); feedback and reports 5 per address in ten minutes and 60 an hour in all; wrong admin codes 5 in 15 minutes per address. Addresses are only kept scrambled and in memory. A new world's first items and its numbers come from the server's own copy of game-data.json.
- Checks: cheats.mjs (things only a changed game would send) and `guards`.

It says only what the code does; when the game keeps something new, change it in the same update. Seen tips are kept on the phone (pocket-life:tips). Nothing more without Luke asking.
