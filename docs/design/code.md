# How the code is laid out

- Files (the same set in test/, the root and releases/<version>/): index.html is the page and a small loader; style.css is the look of the menus and buttons; game/*.js is the game code, one file per topic (three.js r170 from jsDelivr through an import map); game-data.json is all the content. No build step.
- The loader fetches game-data.json fresh, then style.css and the game's parts with its version and build added to their addresses, so phones never mix old and new files. The parts (listed in PARTS in index.html, in order) share one scope: the loader joins them and runs them as one module, exactly like one file. So a part can use anything from an earlier part; keep things in the part for their topic, and add a new part to PARTS (and release.sh copies the whole game/ folder). The parts: core (helpers, renderer, data), land, nature (trees, rocks, bushes, pond plants), plants (tall grass and other cuttable plants), world-build, items (shapes, items, recipes, needs), people (bodies), world-items (things on the ground), you, needs (needs ticking, day and night), inventory (and craft), camera (and graphics), moving (walking, pathfinding, the task queue, tasks, autopilot), input (taps, tap menus, pause, keys), screens (make your person, death, main menu), loop, online (networking and the server's messages), admin, others (other people, walking about, chat), start.
- How to add things: an item or recipe is a game-data.json edit (items, recipes; see its help). A cuttable plant like tall grass is a plants entry. Then run python3 tools/worlds.py test-build so the server knows. A new kind of action needs a handler in server/src/actions.js, a task in game/moving.js (the queue, nextTask) and a tap menu entry in game/input.js (menuActions). Placeables and buildings will get their own shared system (things placed in the world with a kind, position and state, in data) when the first one is built; build it generic so the next ones are data entries.
- game-data.json: all content. Items, recipes, needs (stats), things to use (sources), day and night colours, character looks, body shapes, settings. It has a "help" section explaining each part.
- Adding content should almost always be a small edit to game-data.json, not code. New items automatically appear in the admin's Add list, the Inventory and Craft (with a picture drawn from the 3D model); keep it that way for placeables and buildings when they come.
- The world is settings.worldSize metres square (100 for now), with thick forest past the edge. The clearing round the start is laid out from its own random numbers and the rest of the world from a second set, so changing the world never reshuffles the clearing.
- Keep it light for phones. Lots of copies of a shape are drawn as one InstancedMesh, split into chunks of the map. Grass is only drawn near the camera. Far-off trees use simpler shapes.
- Since 0.0.7 nothing about the game is saved on the phone except settings (graphics, mutes, the admin code) and the phone's random id. The server holds people (one storage key per person, p:<id>), the world, feedback and reports.
- server/ is the online world: a Cloudflare Worker (named pocket-life) with one Durable Object holding the whole world (named live). src/index.js is the World (storage, sockets, hello, the message pipeline, the tick, leaving); its other methods are in files by topic added onto it (persons.js, away.js, nature.js, line.js, admin.js); src/actions.js has one small handler per player message ({ when: any|alive|world, run }); src/shared.js has what they all use (game.json rules, LIMITS, helpers); src/needs.js is needs and inventory maths; src/filter.js the chat filter; game.json and words.json are copied from test/game-data.json by tools/worlds.py test-build (so run it after changing needs, items, sources, away or chatFilter). PROTOCOL in index.js and proto in the game's hello must match. It runs at wss://pocket-life.misty-glade-6e8e.workers.dev/world. Cloudflare builds and deploys it from the server folder on every push to main. The game finds it through "server" in game-data.json.
- Cloudflare free plan (Luke is on it, 0.1.4): 100,000 requests a day (20 incoming WebSocket messages count as 1, plus connections and alarms) and 100,000 storage writes a day; past either, things fail until 00:00 UTC (9:30 am Darwin). So: at most settings.maxPlaying (20) play at once, the rest wait in line on the main menu (server line(), callLine(): 'line' with your place, 'turn' when a spot opens, the game then sends hello again); walks are sent once with where they end (move with tx, tz) plus every 2.5 s, and other games walk them along findPath (heardMove); people are saved straight away after doing something (flush(who)) but walking and needs ticking over at most every 5 minutes (SAVE_EVERY); every storage write goes through put() so it's counted. The Admin panel shows today's use (a.state, usageNow). Phones only draw the 30 people nearest the view (SHOW_PEOPLE, pickShown). If it gets busy, the $5 a month Workers Paid plan removes the daily caps.
- If the frame rate drops below about 45, the game lowers its sharpness a step (pixel ratio), never below 1.
- Respawning things (23 Nov 2026 tidy-up): an item with startInWorld and spawnsNear (trees or boulders) tops up by itself; the server's respawnPlan (server/src/nature.js) reads the amount from game.json and shares spots between items that turn up in the same place, so a new one needs no world reset. Berry names in messages come from the berry bush's harvest, not code.
- Rules the game and the server share (0.3.0): test/game/rules.js is the one copy of every rule both sides work out (needs maths, berries growing back, fires and fuel, seats, kinds of item, where a claim can go, the chat filter). It's the first part of the game (PARTS in index.html), and `python3 tools/worlds.py test-build` copies it to server/src/rules.js (never edit that copy). Change a rule once and both sides change. Keep it plain: no THREE, no page.
- The data check (0.3.0): `python3 tools/worlds.py check` (run by lint.py, and by test-build before it writes anything) reads game-data.json and says in plain words what's wrong: a recipe or source naming an item that doesn't exist, a look with an unknown shape, a weight that isn't a whole number, two plants sharing a seed, a section with no help note, and so on. It also fails if the server's copies (game.json, words.json, src/rules.js, worlds.json's test version) are out of date. So a typo in the data is caught before it reaches the game.
- Guards on the server (0.3.0, server/src/guard.js; found in the 23 Nov 2026 audit): your person has to be within 4 m of what they pick up, pick, cut, chop, mine or put down, and by the pond to drink. The server keeps where your person is: a game that says they jumped across the world, left the map or moved while asleep is sent back ('pos', the game's snapTo). Walks are allowed up to 25 m at once (patchy connections send them late, in bursts), refilled at 1.6 times walking speed. So the server knows where things are, the layout a game sends now also lists every tree, rock, old stump and plant in the game's own order (layoutData in online.js): taken from the first game of each new build, and the admin's game has the final word for that build (needLayout, takeLayout). A new world's first items are checked too (only things with startInWorld, no more than that many). Wrong admin codes: 5 in 15 minutes from one address and that address has to wait. Feedback: 5 per address in ten minutes, 60 an hour in all. Addresses are only kept scrambled and in memory. If one action throws an error, it's logged and the player's game is sent their person again; the world carries on.
- Things that aren't there (found in the 24 Nov 2026 whole-game check, fix waiting for Luke's say): the reach check only held for real things. A number the layout doesn't have (tree 4000, rock 1500, bush 150, old stump 300) fell back to where the person stands, so a changed game got logs, stones and berries from nowhere, without walking. Now `isThing` and `isPlant` (guard.js) refuse a number the layout doesn't have, once the layout is known (it has its trees). A world with no layout yet works as before. tools/tests/cheats.mjs proves both halves (15 lines: it failed 13 before the fix).
- Names and chat nobody can read (same check, same fix branch): text from a game only had control characters taken out, so a name could be made of unseen characters (it looked empty on the name tag, in reports and in the admin's lists) and a mark that makes text read backwards could go in names and chat. Now `clean` (server/src/shared.js) also takes out the unseen marks that hide or reverse text, and `blank` refuses a name or a chat line with nothing in it to see. Accents, other alphabets and emoji are kept as typed. tools/tests/cheats.mjs section F (16 lines: 7 failed before).
- A short break in the connection (0.3.0): for away.comeBackSeconds (15) after a connection goes, the person stays exactly where they are on the server. The game keeps going with its queue, keeps what it finishes in an outbox (online.js: sendAct, flushOutbox; up to 8 things, 30 s), and on reconnecting within that time carries on from where it is, sends the outbox, then asks for its person ('sync'). Longer than that and the person may have strolled off, so the game jumps to where the server has them, as before.
- Loose things on the ground are drawn together (0.3.0): items whose shapes are shared (sharedGeo in items.js: sticks, stones, logs, berries) are copies in one InstancedMesh per shape (world-items.js: batchFor), each with its own place, turn, size and colour. A thousand sticks cost about what one did. Tools and anything with its own shape are still drawn one by one. When adding an item that will lie about in numbers, build its shape with sharedGeo.
- Sticks and stones topping up only saves the world when something was added (it used to save every 5 minutes regardless).
- Bars centred with `left: 50%; transform: translateX(-50%)` (place bar, queue, hint, banner, Joining) need `width: max-content` (and a max-width): without it the browser lays them out in only half the screen, and a longer note squeezed to one word a line (the campfire place bar on Luke's phone, fixed in 0.3.0 build 2).
- Growing without breaking (0.3.1, Luke 23 Nov 2026: "ensure we can keep growing without the game breaking"). Measured with tools/tests/load.py (the real server in memory) and a game with 300 people in the world:
  - Saving people who are away: `touch(p)` saves within SAVE_EVERY (5 min); `touchLater(p)` (someone away who only walked or whose needs ticked over) at most every AWAY_SAVE_EVERY (60 min), since the server plays them forward again from their last save. 300 away and 20 playing nonstop (each doing something every minute, all day): 7,273 writes an hour (174,552 a day, over the free 100,000) before, 3,100 to 4,200 an hour (75,000 to 100,000 a day over 4 runs) after, so that extreme is right at the limit. Nobody playing: 300 away cost 339 an hour (8,136 a day), 1,000 away 1,039 an hour. A tick takes about 5 ms with 300 away and nobody playing, about 55 ms with 20 playing (on this machine).
  - Picking berries saves and tells everyone once however many were picked (takeBerries in nature.js); an away person only saves after a walk if they picked something.
  - Errors: the server's tick (per person) and each message are caught; noteError logs it and adds a "Server error (where)" note to the Inbox, once an hour per problem. In the game, frame() in loop.js catches an error in a frame and carries on; reportError (online.js) sends each problem once (5 a visit at most) as an auto feedback note "Game error (where: message)" with a short trace, by socket or POST /feedback. Auto notes that repeat are counted ("· N times, last ...") instead of filling the Inbox.
  - me.said (what someone said lately, kept for reports) is trimmed so the socket's attachment stays under Cloudflare's 2 KB.
  - Other people: only the nearest GRAPHICS[gfx].people (30 high, 20 medium, 12 low) are drawn, and only they have a body. The rest are a hidden marker that keeps their place; showBody (others.js) makes the body when they come near and throws it away when they go. A phone with 300 people in the world: 958 meshes instead of 6,278, 25 MB of memory instead of 46 MB (20 drawn, medium graphics).
  - Routes no longer clip the edges of rocks and bushes: findPath's grid is half-metre cells, so a straight line it allowed could pass up to about 0.3 m into something. clearLine now checks a line the grid allows again at the exact spots (solidAt with 0.05 m to spare, and the pond), except within 0.5 m of either end. Found by the strolling check (someone away brushed through a bush's edge for a few seconds).
  - Still open as it grows (not fixed): each pick-up or drop costs 2 writes (world and person), so lots of busy players reach the free limit again (fix: group saves, or the $5 Workers Paid plan); the whole world is one stored value (2 MB cap); every person is loaded at start and listed in each welcome (about 130 KB with 1,000 people); the free plan's CPU limit for the tick isn't confirmed (Cloudflare's pages disagree: 10 ms or 30 s); only about 18 claims fit in the 100 m world (about 24 packed perfectly), so land runs out before the server does.
- Who's connected (0.3.2): sockets() works out every connection and its attachment once and keeps it until something changes, and socketOf(who) / isOnline(who) look people up in a map (socketOf prefers the connection still playing them if two do for a moment). fresh() clears it at the start of every message, tick, connection and close, and attach(ws, me) saves an attachment and clears it. Always use this.attach, never ws.serializeAttachment, or the list goes stale. Before this, every "is this person online?" unpacked every connection again, so a tick cost people in the world x people online. load.py, 20 playing: 300 away 47 ms a tick before, 5 ms after; 1,000 away 147 ms before, 16 ms after.
- Restore (0.3.2): server/src/restore.js, see admin.md. Cloudflare's point-in-time recovery keeps 30 days of the Durable Object's storage, so that's the backup. It doesn't work in local development; tools/tests/server.mjs keeps its own history (every storage change is a point, bookmarks name them, ctx.abort restarts the World), and its storage.list now returns copies like Cloudflare's.
