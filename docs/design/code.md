# How the code is laid out

- Files (the same set in test/, the root and releases/<version>/): index.html is the page and a small loader; style.css is the look of the menus and buttons; game/*.js is the game code, one file per topic (three.js r170 from jsDelivr through an import map); game-data.json is all the content. No build step.
- The loader fetches game-data.json fresh, then style.css and the game's parts with its version and build added to their addresses, so phones never mix old and new files. The parts (listed in PARTS in index.html, in order) share one scope: the loader joins them and runs them as one module, exactly like one file. So a part can use anything from an earlier part; keep things in the part for their topic, and add a new part to PARTS (and release.sh copies the whole game/ folder). The parts: core (helpers, renderer, data), land, nature (trees, rocks, bushes, pond plants), plants (tall grass and other cuttable plants), world-build, items (shapes, items, recipes, needs), people (bodies), world-items (things on the ground), you, needs (needs ticking, day and night), inventory (and craft), camera (and graphics), moving (walking, pathfinding, the task queue, tasks, autopilot), input (taps, tap menus, pause, keys), screens (make your person, death, main menu), loop, online (networking and the server's messages), admin, others (other people, walking about, chat), start.
- How to add things: an item or recipe is a game-data.json edit (items, recipes; see its help). A cuttable plant like tall grass is a plants entry. Then run python3 tools/worlds.py test-build so the server knows. A new kind of action needs a handler in server/src/actions.js, a task in game/moving.js (the queue, nextTask) and a tap menu entry in game/input.js (menuActions). Placeables and buildings will get their own shared system (things placed in the world with a kind, position and state, in data) when the first one is built; build it generic so the next ones are data entries.
- game-data.json: all content. Items, recipes, needs (stats), things to use (sources), day and night colours, character looks, body shapes, settings. It has a "help" section explaining each part.
- Adding content should almost always be a small edit to game-data.json, not code. New items automatically appear in the admin's Add list, the Inventory and Craft (with a picture drawn from the 3D model); keep it that way for placeables and buildings when they come.
- The world is settings.worldSize metres square (100 for now), with thick forest past the edge. The clearing round the start is laid out from its own random numbers and the rest of the world from a second set, so changing the world never reshuffles the clearing.
- Keep it light for phones. Lots of copies of a shape are drawn as one InstancedMesh, split into chunks of the map. Grass is only drawn near the camera. Far-off trees use simpler shapes.
- Since 0.0.7 nothing about the game is saved on the phone except settings (graphics, mutes, the admin code) and the phone's random id. The server holds people (one storage key per person, p:<id>), the world, feedback and reports.
- server/ is the online world: a Cloudflare Worker (named pocket-life) with one Durable Object holding the whole world (named live). src/index.js is the World (storage, sockets, hello, the message pipeline, the tick, leaving); its other methods are in files by topic added onto it (persons.js, away.js, nature.js, line.js, admin.js); src/actions.js has one small handler per player message ({ when: any|alive|world, run }); src/shared.js has what they all use (game.json rules, LIMITS, helpers); src/needs.js is needs and inventory maths; src/filter.js the chat filter; game.json and words.json are copied from test/game-data.json by tools/worlds.py test-build (so run it after changing needs, items, sources, away or chatFilter). PROTOCOL in index.js and proto in the game's hello must match. It runs at wss://pocket-life.misty-glade-6e8e.workers.dev/world. Cloudflare builds and deploys it from the server folder on every push to main. The game finds it through "server" in game-data.json.
- Cloudflare free plan (Luke is on it, 0.1.4): 100,000 requests a day (20 incoming WebSocket messages count as 1, plus connections and alarms) and 100,000 storage writes a day; past either, things fail until 00:00 UTC (9:30 am Darwin). So: at most settings.maxPlaying (20) play at once, the rest wait in line on the main menu (server line(), callLine(): 'line' with your place, 'turn' when a spot opens, the game then sends hello again); walks are sent once with where they end (move with tx, tz) plus every 2.5 s, and other games walk them along findPath (heardMove); people are saved straight away after doing something (flush(who)) but walking and needs ticking over at most every 5 minutes (SAVE_EVERY); every storage write goes through put() so it's counted. The Admin panel shows today's use (a.state, usageNow). Phones only draw the 30 people nearest the view (SHOW_PEOPLE, pickShown). If it gets busy, the $5 a month Workers Paid plan removes the daily caps.
- If the frame rate drops below about 45, the game lowers its sharpness a step (pixel ratio), never below 1.
- Respawning things (23 Nov 2026 tidy-up): an item with startInWorld and spawnsNear (trees or boulders) tops up by itself; the server's respawnPlan (server/src/nature.js) reads the amount from game.json and shares spots between items that turn up in the same place, so a new one needs no world reset. Berry names in messages come from the berry bush's harvest, not code.
